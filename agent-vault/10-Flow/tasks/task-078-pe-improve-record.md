## 0. 결론 (불편한 사실 먼저)

**판정: 이력서 L1·L2·L3 의 숫자 기준은 모두 충족 → 합격. 운영 `topicWords.ts` 를 `topicWords@v3` 로 고쳤다. 다만 «얇은 합격»이다.** 합격선을 넘긴 폭이 작고 측정 한계가 크다.

**불편한 사실 6개 (Leader 결정에 영향)**
1. **예산을 2회 초과했다(내 실수).** 계획한 25회(N2×10·N3×6·N5×6·대조×3)는 그대로 썼고, 그 뒤 «측정 문구 = 운영 문구» 동일성을 보려고 쓴 `node -e` 가 하네스 파일을 import 했다. 하네스는 import 시 `main()` 이 돌아 **DRY 없이 라이브 호출 2회**(`N2-v0` 12/10장 · `N3-v0` 13/10장, 운영 문구 = v3, 기본 계획 diag)가 나갔다. 저장된 행 2개·남은 프로세스 0·세 번째 호출 흔적 없음. **총 라이브 호출 27회(승인 25)**. 이 2회는 판정 표(25회)에서 뺐고 §2.5 에 따로 적었다 — 넣어도 판정은 안 바뀐다. 재발 방지로 하네스에 «직접 실행일 때만 `main()`» 가드를 넣었다.
2. **L1 = 8.1장은 합격선 8.0 에 +0.1 이다.** 세트 10개의 sd 2.6 → 95% 신뢰구간 약 6.2~10.0. 우연으로 설명 가능한 수준이며 «8.0 이상»과 «8.0 미만»을 가를 표본이 아니다. 같은 입력(N2 variant 0)을 세 번 돌린 통과가 8·12·12장(자르기 전)으로 흔들렸다.
3. **한 세트가 라벨 부풀리기로 통과를 채웠다.** `N2-v0#2`(10장)는 レストラン·公園·スポーツ(사전 N5)·計画(사전 N4) 등 기초어를 N3·N2 로 달아 창을 통과했다. 이 세트를 «부풀리기 의심»으로 빼면 N2 평균은 **7.9(< 8.0)** 가 된다. 내가 넣은 «실제 급수를 쓰고 [수준]에 맞추려고 바꾸지 않습니다» 문장이 이 세트에서는 못 막았다.
4. **N2 통과의 86%(74/86)가 N3 라벨, N2 라벨 10, N1 0.** 규칙(±1)이 N3 를 허용하니 통과로 세지만, N2 를 고른 학습자가 받는 새 단어는 «N3 급» 이 주다. 사전 급수 평균은 N2 전체 4.17 → 3.62(필요한 이동 −2 의 약 28%) — 진짜 이동은 있으나 작다. 반면 N3 는 4.27(대조) → 3.35 로 거의 한 단계(−0.92)를 움직였다.
5. **모델 라벨이 사전보다 «어렵게» 기운다.** N2 모델−사전 평균 편향이 진단 +0.03 → **−0.31**(사전과 짝지어진 45개 중 어렵게 단 것 25·같은 것 10·쉽게 단 것 10). 급수를 깎지 않던 모델이 올리는 쪽으로 움직였다 — L5 가 경계한 방향이다. 또 `[이번 초점]` 중 «수량·시간·위치»(2장)·«인사·감사·사과»(6장)는 수준이 높아도 N4~N5 어휘로 새서 통과가 크게 준다(§3.3).
6. **지연이 늘었다.** 전체 p95 11.86초(진단 10.72초 — 기준 12초에 0.14초 여유), N2 만 보면 최대 12.12초로 12초를 넘는다. 단 **A12 `topicWords` 엔진 한도는 20초**(벽시계 30초, `engine/router/tasks.ts:42`·`topicSet.ts:35`)이고, L3 의 «12초 fail-fast» 는 A1(`talk`)의 값이다 — L3 문구의 근거가 실제 한도와 다르다(Leader 확인 요청).

**운영에 반영한 것**: `topicWords.ts` 프롬프트 문구 3곳 + 버전 `topicWords@v3` + 버전 설명 주석. 측정한 변형과 **바이트 단위로 같다**(git HEAD 의 옛 시스템 프롬프트에 하네스 치환 3곳을 적용한 결과 = 현재 운영 시스템 프롬프트, `IDENTICAL`). tsc 0 · eslint 0. **기존 시험 8건이 깨진다**(`topicWords.test.ts` — 목록 §5, developer 몫). 라우트·스키마·검사 코드는 건드리지 않았다.

## 1. 변형 설계 (호출 전 기록)

### 1.1 진단이 알려 준 것과 이 변형이 겨냥하는 곳

- 진단 `[확실]`: 탈락 72/72 = `JLPT_WINDOW`. 모델이 N2 를 요청받아도 급수를 N2·N1 로 단 적이 0/78, 창 밖(N4 40·N5 23)이 81%. 모델 급수와 사전 급수는 ±1 일치 93% — **라벨이 거짓이 아니라 고른 단어가 쉬운 것**이다.
- 현 프롬프트 구조 `[확실]`(파일 직접 읽음): `[수준]` 은 `jlpt` 칸 규칙(239행)과 예문 어휘 줄(242행)에만 나오고, **단어 고르는 기준(231행 «일상 회화에서 실제로 쓰는»)에는 수준이 없다.** 게다가 출력 키 순서가 `textJa → reading → meaningKo → chunkType → jlpt → valid` 라서 `jlpt` 는 단어를 **쓴 뒤에** 달리는 꼬리표다 — 라벨 규칙이 단어 선택을 바꿀 길이 구조적으로 없다. 239행 예시도 «N5 → N5·N4» 하나뿐이라 아래 방향 예시만 있고, 문장 끝 «그보다 어려운 단어는 내지 않습니다» 는 N2 에서는 비어 있는 규칙이면서 «쉽게 내라» 로 읽힐 여지가 있다([추측]).
- 따라서 **단어 선택 단계(상류)에 수준을 올리는 것**이 이번 변형의 핵심이다. 진단 §5 후보 1(선택 기준에 `[수준]` + 하한) + 239행 개정을 합친 하나다. 후보 2(고정 예시 단어)는 일부만(아래 negative 예시로) 쓰고, 후보 3(문형 → 단어 방향)은 쓰지 않는다.

- **치환 방식**: 하네스가 운영 `req.system` 에 `from → to` 치환 3곳을 바이트 일치로 적용(앵커가 정확히 1번이 아니면 던진다). 합격하면 운영 파일의 해당 3곳을 같은 `to` 로 바꿔 **측정한 문구 = 출하 문구**가 되고, DRY 가 동일성을 점검한다.

### 1.3 길이 (DRY, 호출 0회)

- system 1,626자 → 1,943자(**+317자, +19.5%**). user 블록 180자 불변. 전체 프롬프트(진단에서 `promptChars` 2,817~2,830) 기준 ≈ +11% 로 어림 — 실측은 호출 뒤 `promptChars` 로 적는다. 지연 여유는 12초 fail-fast 대비 진단 최대 10.7초라 1.3초 — **지연은 p95 를 직접 재서 판정한다**(L3).
- 어려운 단어는 읽기(가나)·뜻이 길어져 출력이 늘 수 있다(출력이 지연의 지배 항) — 이것도 같은 지표로 본다.

### 1.4 호출 전 예상(사전 등록, 틀릴 수 있다 — `[추측]`)

- N2 라벨이 N4·N5 → N3 중심으로 이동하고 N2 가 처음 나타난다. 통과 평균은 6~9장대로 본다(≥ 8.0 달성 확률 절반 안팎).
- 위험 4가지: ① 어려운 한자어에서 `valid:false`·`READING_MISMATCH` 증가(요청 13 → 목표 10 여유 3장이 줄어듦) ② `jlpt` null 통과 증가(«모르면 null» 문구 — L3 ≤10%) ③ **라벨 부풀리기**(통과는 늘었는데 사전 급수가 여전히 N5·N4) — gate 의 `inflationCheckN2` 로 점검 ④ 지연 증가.
- 판정은 호출 수가 아니라 이 기록의 표로만 한다. 범위 밖: 검사 ⑤ 창·`assembleTopicWords`·스키마·입력 줄(= developer 몫)은 이번 소환에서 건드리지 않는다.

### 1.5 채택하지 않은 변형 (이유)

- **`jlpt` 를 `textJa` 앞으로**(라벨 먼저 → 자기회귀로 단어를 라벨에 맞춤): 가장 강한 레버일 수 있으나 ① 스키마 `required` 순서 변경 = L5 «출력 스키마·키 그대로» 와 충돌 ② 모델이 라벨을 먼저 약속하고 쉬운 단어를 달면 **라벨 부풀리기를 구조적으로 유도**. 사용자 승인 예산 밖 — 필요하면 사용자 질문 사항.
- **긍정 예시 단어(N2 → 日程·延期…)**: 주제 안 단어면 베끼기로 통과 장수가 부풀어 측정이 오염된다. 주제 밖 단어면 주제 밖 출력을 부른다.
- **후보 3(문형 → 단어 방향)**: 수준 차이 ≥2 일 때만 켜려면 입력 줄이 필요해 developer 사양 협의가 필요하고, 통과가 오히려 줄 수 있다(진단 §5).

## 3. 해석

### 3.1 변형의 작동 `[확실]`(이번에 직접 측정) / 이유는 `[가능성 높음]`

- 결과는 변형이 의도한 방향으로 움직였다: N2 통과 2.5 → 8.1, N3 의 사전 평균 급수 4.19 → 3.35, N2 의 모델 라벨이 N4·N5 중심에서 N3 중심으로. 이 소환의 사전 질문(«문구 239행이 원인인가»)에는 **단어 선택 기준에 수준을 넣는 쪽이 효과가 있었다**는 답이 나왔다. 단 세 곳을 한꺼번에 바꿨으므로 **어느 곳이 기여했는지는 분리하지 못했다**([추측]: 새 `- 난이도:` 줄(B)이 주된 요인).

### 3.2 «얇은 합격»인 이유 `[확실]`

- 합격선 +0.1 · 신뢰구간 6.2~10.0 · 같은 입력 세 실행 8/12/12 · 한 세트 제외 시 7.9. 그리고 통과의 86%가 N3 라벨(N2 10·N1 0)이라 «N2 를 고른 사용자가 받는 단어»는 대부분 «N3 급» 이다. 사전 급수 평균의 실제 이동은 필요한 −2 의 약 28%.

### 3.3 `[이번 초점]` 별 N2 통과 `[확실]`(세트당 n=1~2, 방향만)

| 초점(variant) | 통과 | 초점(variant) | 통과 |
|---|---|---|---|
| 0 명사 | 8 · 10 | 4 질문·안내·권유 | 10 · 7 |
| 1 동사 | 10 | 5 부탁·질문·확인 | 10 |
| 2 형용사 | 8 | 6 인사·감사·사과·맞장구 | **6** |
| 3 수량·시간·위치·방법(부사·수식) | **2** | 7 덜 흔하지만 알아 두면 좋은 표현 | 10 |

- 3 은 부사·시간 표현(朝早く·午後から·どこかへ·ずっと·かなり …)이 성격상 N4 이고 모델이 N4 라벨을 솔직히 달아 대부분 창 밖. 6 은 ありがとうございます·いいですね·わかりました(N5·N4). **운영에서는 `variant` = 이 주제로 새 단어를 만든 날 수라 8일 주기 중 이틀(4번째·7번째 날)이 이 약한 초점을 만난다** → 그날은 통과가 2~6장이라 B1 로 채운다. 두 세트를 빼고 읽으면 9.1(설명용이지 판정용 아님).
- 이 약점은 이번 변형의 범위 밖(`TOPIC_WORDS_FOCUS` 문구)이며 **두 번째 변형이라 예산 밖** — 사용자에게 물을 사안(§8).

### 3.4 문체·주제 이탈 눈 점검 `[가능성 높음]`(비원어민 판단)

- N2 통과 단어는 대체로 주제(주말 계획) 안이다. 정중·업무풍 표지(ご都合·確認させていただきたいのですが·申し訳ありません·了解しました·いかがですか·おすすめ…)는 통과 86개 중 9개(10.5%, 진단 15개 중 1개 6.7% — 표본이 작아 증가라고 단정 못 함). **어휘 난이도 대신 정중도로 올라간 비율은 크지 않다.** 단 `확인させていただきたいのですが`(긴 문형)·`了解しました`(업무체)는 주말 약속 주제로는 격식이 과하다.
- 예문 `exampleJa·exampleKo` null 비율: v2·v3 모두 **0%**(통과 단어 기준, 저장된 응답 재계산) — IMP-0056(예문 빈 카드)을 이번 변형이 악화시키지 않았다.

## 7. 발견한 것 중 이번 범위 밖 (새로 만들지 않음 — 기존 IMP 대응만)

- **중국 간체자 오표기**(`怎样ですか` — 모델이 `valid:false` 로 자기 신고해 걸렸으나 검사 ②는 간체자를 못 거른다): IMP-0055·0056·0057 **어느 것에도 해당하지 않는다**(0057 은 읽기 가나 종류, 이건 표기 문자 검사 문제). 1건 관찰이라 빈도 미확인 — Leader 가 접수 여부 판단.
- 한국어 뜻에 군더더기·어색한 풀이가 붙는 경우(`休む → 쉬다, 쉴 예정이다` · `集まる → 모이다, 모인다` · `何時集合ですか → 몇 시에 집합하나요`): **IMP-0055(어색한 한국어 뜻)와 같은 부류**다. 단 IMP-0055 가 적은 **한자음 직역형(수접·시착실·영수서 류)은 이번 표본에서 보지 못했다**.
- 예문 빈 카드: 이번 측정에서는 통과 단어 265개 전부 예문이 있어 **IMP-0056 해당 사례 없음**(0%).
- 외래어 읽기가 히라가나로 나오는 경우(`レストラン→れすとらん`·`キャンプ→きゃんぷ`·`ショッピング→しょっぴんぐ`·`スポーツ→すぽーつ`·`コンサート→こんさーと`, 세트에 따라 `レストラン→レストラン`(가타카나)과 `れすとらん` 이 섞여 나옴): **IMP-0057 에 정확히 해당**한다.

## 8. 사용자·Leader 에게 필요한 결정 (결정은 내가 하지 않는다)

1. **합격선 +0.1 을 합격으로 확정할지.** 더 확실하게 하려면 N2 를 몇 세트 더(예: 10세트) 돌려야 하고 이는 승인 예산 밖이다. 이미 2회 초과한 상태라 추가 호출은 사용자 승인이 먼저다.
2. **두 번째 변형을 시도할지(예산 밖)**: ① 약한 초점(3·6)을 수준 인식형으로 고치는 방안(`TOPIC_WORDS_FOCUS` 문구, 프롬프트만) ② 부풀리기 대응(N2 라벨 N3 통과가 많으니 «N2 가 목표면 N3 만으로 채우지 않는다» 류 — 다만 «거짓 급수를 유도하지 않는다»는 L5 와 긴장) ③ 검사 ⑤ 창·사전 보정(이력서 L5 에 따라 프롬프트로 부족할 때만 사용자에게 따로 묻는 항목 — 이번에는 L1 을 넘어 해당하지 않는다).
3. **기존 시험 갱신 사양**(§5): 길이 상한을 올릴지 문구를 줄일지.
4. **L3 지연 기준 값**: «12초» 의 근거가 A1 값이라 A12 실제 한도(20초)와 맞는지 확인. 기준을 20초 한도 기준으로 다시 잡으면 N2 최대 12.12초는 여유가 크다.

## 9. 함정 기록 (재발 방지)

- **라이브 하네스는 import 부수효과 금지.** `node -e "import('…live.ts')"` 만으로 `main()` 이 돌아 DRY 없이 호출 2회가 나갔다 → 가드 추가(직접 실행일 때만). 동일성 점검 같은 일은 `ident-check.mjs`(스크래치패드)처럼 **파일 이름이 하네스와 다른 스크립트에서** import 하고, 하네스를 만질 때는 반드시 `DRY=1` 부터. 같은 사고가 나지 않도록 다른 라이브 하네스(`tests/live/*`)도 import 안전한지 점검하면 좋다(미점검).
- `quantile()` 의 p95 는 표본 ≤25 에서 사실상 최댓값 근처다 — 지연 기준을 p95 로 두면 한 번의 느린 호출에 판정이 흔들린다.
