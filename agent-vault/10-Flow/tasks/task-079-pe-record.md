1. **(b) 의 합격은 재실행 1회에 기댄다.** 처음 실행 그대로는 9세트 7.56 으로 합격선 7.6 에 **0.04 모자랐고**, 한 세트가 20초 타임아웃이었다. 같은 입력을 예비 호출 1회로 다시 불러 13장 중 10장이 통과해 10세트 평균 7.8 이 됐다. 재실행은 사전 등록된 용도(예비 = 재실행용)이고 합격선은 건드리지 않았지만, **세트별 sd 1.93·표본 10 이라 7.56 과 7.8 은 통계적으로 구분되지 않는다** — «v4 가 N2 를 깎지 않았다»가 아니라 «깎았다는 증거도 없다»까지만 말할 수 있다. v3(8.10)보다 −0.3 은 task-078 의 신뢰구간(6.2~10.0) 안이다.
2. **20초 타임아웃 1건.** 31호출 중 1건(v4 호출 21건 중 1건, v3 10건 중 0건). 이 실행의 v4 중앙 지연은 v3 보다 짧고(0.92배) 타임아웃 전후 호출은 8~13초라 **v4 의 구조적 지연 증가로 보이지 않는다**(`[가능성 높음]`, 1건이라 확정 못 함). task-078 의 v3 25호출은 최대 12.12초였고 타임아웃이 없었다. 운영에서는 타임아웃이면 B1 풀로 채운다(통과 0장). v4 도입 후 운영 지연 지표 관찰을 권한다.
3. **효과가 입력에 따라 크게 다르다.** 합성 명사 중심 입력에서는 보조 뜻을 단 단어가 49% → 19% 로 크게 줄었지만, 실제 운영에서 N2 가드로 쓰는 `weekend-plan` N2 입력(표현·동사 비중이 큼)은 43.2%(task-078 v3) → 38.5% 로 거의 안 줄었다. 사무 용어 입력 P09(회사 업무 대화)는 v4 가 오히려 10/10 이 보조 뜻을 달았다. 즉 **v4 의 «보조 뜻을 줄인다» 효과가 «틀린 보조 뜻을 줄인다» 로 이어졌는지는 눈가림 판정(a)에서만 알 수 있다.** 줄어든 비율만으로 (a) 를 예단하지 않는다.
4. **새 부작용: 같은 낱말 반복.** P09 v4 에서 `業務 → 업무, 업무`·`同僚 → 동료, 동료`·`報告 → 보고, 보고` 3개(v3 arm 0건). 한국어 뜻이 한자음과 같은 단어에서 «한자음을 뒤집지 말라 + 보조 뜻을 붙이라» 가 충돌해 같은 낱말을 한 번 더 적은 것으로 보인다(`[추측]`). 뜻은 틀리지 않지만 어색하다(판정은 Leader). **LLM 호출 없이 고칠 수 있다**: `assembleTopicWords` 가 같은 토큰을 접도록(`업무, 업무` → `업무`) 코드에서 처리하는 것이 안전하다 — developer 몫이라 사양만 전달한다.
5. **예상과 어긋난 것**: 호출 전 예상 «v3 의 보조 뜻 비율 35~40%» → 실제 49%(합성 입력에서). 예상 «v4 15% 안팎» → 19%. 예상 «(b) 통과 확률 절반 안팎, 쉬운 단어 쪽으로 기울 위험» → 통과했으나 얇다. 예상 «(d) 통과» → 맞음(v4 가 오히려 짧고 빠름). 예상 «(c) 큰 변화 없음» → 맞음.
6. **통과율 (c) 는 변별력이 약한 조건이다.** 입력이 합성 주제·제외 목록 비움이라 v3·v4 모두 95~97% 로 천장에 가깝다. «v4 가 통과율을 깎지 않는다» 는 이 조건에서만 확인된 것이고, 제외 목록이 쌓인 깊은 체인(뜻 중복 검사 ⑦ `DUP_MEANING` 이 많이 걸리는 구간)은 측정하지 않았다.

### 2.6 한계 (숨기지 않는다)

- 단일 모델(haiku)·입력당 표본 1개(arm 별 10회, 단어 100개)·**첫날 조건(제외 목록 비움 — 가드는 기본 표현 12개)**·합성 주제 8종(AI 가 만든 일반 주제, 사용자 데이터 0)·뜻 판정자는 AI(Leader) 한 명이다. 저장된 57개의 12% 는 실제 사용자 주제에서 나온 비율이고 이번 입력과 같은 분포가 아니다.
- v3 arm 의 «어색+틀림» 비율이 이번 합성 입력에서 12% 근처로 나온다는 보장이 없다. 판정 결과 v3 비율이 낮으면 (a) 의 «절반·6% 이하» 는 판단 근거가 약해진다(분모가 작음) — Leader 판정 뒤 `gate_a` 와 함께 두 arm 의 불량 단어 수 절대값을 같이 읽어야 한다.
- 예시 단어 `定食` 이 프롬프트에 들어가므로 식당 주제에서 같은 단어를 베낄 수 있다. 이번 측정의 식당 입력(P10)에서는 확인하지 않았다.
- 같은 입력을 한 번씩만 불러 호출 간 흔들림(task-078 에서 같은 입력 세 번이 8·12·12장)을 쓰지 않는다.

## 6. 함정 기록 (재발 방지)

- 라이브 하네스는 **직접 실행 + 명시적 `GO=1` 둘 다** 있어야 호출한다. 기본은 DRY. 호출 직전 원장에 먼저 쓰고, 같은 호출 id 는 실패해도 다시 부르지 않으며, 재실행은 `RERUN`+`RESERVE_REASON` 이 있어야만 돈다.
- 타임아웃은 «측정 실패»가 아니라 «측정 결과»이기도 하다(운영에서는 B1 로 채운다). 재실행으로 세트를 채울 때 처음 실행 그대로의 수치와 실패를 0으로 센 수치를 **항상 같이** 적는다(하네스 `guard.sensitivity`).
- 눈가림 표의 단어 수 비교로 arm 이 드러난다(v4 가 뜻 개수가 적다) — 눈가림은 «어느 쪽이 좋은가» 편향을 줄이는 것이지 완전한 차단이 아니다.
- 병렬 에이전트(developer)가 NFS `topicWords.ts` 를 편집 중이다(`hasChineseOnlyHanzi` import 가 이미 보임). 측정은 미러의 HEAD(725007c) 사본으로 했고, 이후 `sync-local` 을 다시 돌리지 않았다 — 측정 중 검사 코드가 바뀌어 통과율이 오염되지 않게 하려는 것이다. 적용 시점의 NFS 파일에서 `Edit` 으로 내 줄만 바꾼다.
