## 현상

(사용자 원문, 2026-10-07) "앱에서 메뉴이동시 화면이 깜빡이는 현상이 있는데 이건 DB조회가 느려서인건가? 해당현상에 대한 원인확인해줘."
> 3번의 경우에는 개선안중에 '불러오는 중' 화면을 띄우고 실제 화면으로 전환할 경우 아무리 빨리 처리되더라도 깜빡이는 것처럼 보일수있을것같아. '불러오는 중' 화면은 제거하고 메뉴를 클릭하면 우선 빈데이터로 해당 화면을 렌더링하고 DB조회 후 데이터를 세팅하는 형태로 처리하면 깜빡이는 느낌도 없고 자연스러울 것같아.

원인 확인(Leader, 2026-10-07, 측정·코드 읽기): DB 가 느린 것이 아니다 — 탭 페이지 SSR 3~12ms·마운트 직후 API 4~19ms(운영 localhost, QA 계정). 각 탭이 마운트 때마다 `loading` 으로 시작해 카드·목록 안의 "불러오는 중…"/스켈레톤을 그린 뒤 API 2~7개를 병렬로 불러 응답이 따로 도착하고(`useKeyedResource` 캐시 없음), 모바일 에뮬레이션(왕복 150ms 가정)에서 로딩 표시 200~330ms·본문 높이 780→1040px(오늘 탭)·화면 상태 5번 전환. 탭을 누른 뒤 서버 렌더 왕복(211~747ms) 동안 이전 화면이 그대로 남는 구간도 있다. 측정 원 출력은 이 세션 scratchpad `flicker-slow.txt` (측정 스크립트의 CLS 집계는 탭 직후 500ms 이내 이동을 빼므로 높이 점프(px)로 재측정 필요).

## 기대하는 모습

사용자 제안: '불러오는 중' 화면을 없애고, 메뉴를 누르면 우선 빈 데이터로 화면을 그린 뒤 DB 조회 후 데이터를 채워 깜빡임 없이 자연스럽게.

디자이너·개발자 검토 결론(Leader 정리):
- "빈 데이터" 그대로는 "없음"으로 읽혀 가짜 빈 상태·가짜 CTA 가 뜬다(오늘 탭 [기본 단어 50개 넣기]·[시작하기], 회화 "아직 채팅이 없어요"). 권고는 **같은 높이의 정적 자리표시(B)** → 탭 누름 즉시 반응(`useLinkStatus` 류) → (선택) **탭 전환 사이 마지막 데이터 캐시(C)**. 지연 표시(D)는 단독 비권고.
- 작업 분할 안: T1 designer 가이드 → T2 공용 자리표시+회화·단어장 → T3 오늘 탭 → 측정 → T4 캐시 모듈(사용자별 키·로그아웃 비움·무효화 epoch) → T5(선택) C 확장.
- 주의: C 의 사용자 간 데이터 노출 방지·오래된 [시작] 버튼·"실패하면 지난 값을 유지하지 않는다"(챌린지 오늘 훅 가이드 §5) 규칙 충돌·`prefetch` 금지(오늘 탭 API 가 복습 판단 잡을 만듦).
