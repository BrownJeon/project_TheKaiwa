# 일본어 회화 앱 관리자/개발자 AI Engine Console 추가 기획

## 78. Admin / Developer Console 도입

일반 사용자는 STT/TTS/LLM의 내부 구현이나 JSON 설정값을 알 필요가 없다.

반면 관리자와 개발자는 다음 정보를 확인하고 일부 값을 조정할 수 있어야 한다.

```text
현재 어떤 Engine이 사용 중인가

어떤 모델이 로딩되어 있는가

어떤 Connection Profile이 활성화되어 있는가

실제 적용 중인 Runtime 설정값은 무엇인가

각 설정값의 기본값은 무엇인가

설정값이 어디에서 변경되었는가

현재 Engine 상태는 정상인가

특정 설정으로 실제 STT/TTS/LLM 호출이 성공하는가
```

이를 위해 일반 사용자 설정과 별도로 `AI Engine Console`을 제공한다.

---

# 79. Console 접근 권한

Console은 일반 사용자에게 노출하지 않는다.

권한 예:

```text
USER

ADMIN

DEVELOPER

SUPER_ADMIN
```

기본 권한:

```text
USER
→ 일반 설정만 사용

ADMIN
→ Voice / Engine / Connection 관리

DEVELOPER
→ 상세 Engine Parameter / JSON / Runtime 설정 확인

SUPER_ADMIN
→ Credential 연결 / 시스템 전체 설정
```

모바일 앱 내부에 포함할 경우에도 Role 기반으로 숨긴다.

예:

```text
설정

├─ 일반 설정
│
├─ AI 선생님
│
└─ 관리자
      ↓
   AI Engine Console
```

또는 개발 빌드에서는:

```text
Developer Mode

Settings
  ↓
AI Engine Console
```

형태로 접근한다.

운영 환경에서는 별도의 Admin Web Console로 분리할 수도 있어야 한다.

# 82. Effective Configuration 화면

관리자/개발자에게 가장 중요한 화면 중 하나다.

단순히 DB 설정값만 표시하지 않고 **현재 애플리케이션에서 실제로 사용되는 최종 설정값**을 보여준다.

이를 `Effective Configuration`이라고 정의한다.

예:

```text

engine
REAZON

connection
reazon-local

provider
cpu

threads
4

greedy_search
```

# 83. 설정값 Source 표시

각 설정값 옆에는 값이 어디에서 왔는지 표시한다.

예:

```text
Setting                  Value            Source

engine                   REAZON           Database

numThreads               4                application.yml

provider                 cpu              Default

timeoutMs                10000            Environment

modelPath                /models/reazon   Connection Profile
```

가능한 Source:

```text
DEFAULT

SOURCE_CODE

APPLICATION_CONFIG

ENVIRONMENT

DATABASE

CONNECTION_PROFILE

USER_SETTING

RUNTIME_OVERRIDE
```

이 기능은 개발자가 문제를 분석할 때 중요하다.

예를 들어:

```text
application.yml에는 threads=8인데

실제 Runtime에서는 threads=4
```

라면 Console에서:

```text
threads

Effective Value
4

Source
Environment Variable

ENV:
SPEECH_THREADS=4
```

처럼 확인할 수 있어야 한다.

각 Engine이 어떤 설정을 지원하는지 확인할 수 있도록 한다.

예:

```text

Enum

Compute Type
Enum
float16 / int8 / default

CPU Threads
Integer
Default: 4

Workers
Integer
Default: 1
```

Schema에는 다음 Metadata를 포함한다.

```json
{
  "key": "cpuThreads",

  "type": "INTEGER",

  "default": 4,

  "min": 1,

  "max": 32,

  "runtimeEditable": true,

  "restartRequired": false,

  "description": "CPU inference thread count"
}
```

# 87. Runtime Editable 설정 구분

모든 설정값을 Runtime에서 수정할 수 있게 하면 안 된다.

각 설정은 다음 속성을 가진다.

```text
READ_ONLY

RUNTIME_EDITABLE

RESTART_REQUIRED

REDEPLOY_REQUIRED

SECRET
```

예:

```text
TTS Timeout
→ RUNTIME_EDITABLE


Whisper Model
→ RESTART_REQUIRED 가능


Docker Image
→ REDEPLOY_REQUIRED


API Key
→ SECRET
```

UI에서도 이를 명확히 표시한다.

# 90. JSON Editor 안전장치

Raw JSON을 직접 수정하는 경우 반드시 Schema Validation을 수행한다.

```text
JSON 수정

↓

JSON Syntax Validation

↓

Engine Configuration Schema Validation

↓

Dependency Validation

↓

Dry Run

↓

Apply
```

예:

```text
cpuThreads = -1

↓

Validation Error

cpuThreads must be >= 1
```

잘못된 설정이 Runtime에 직접 적용되지 않도록 한다.

# 91. Form / JSON 양방향 동기화

개발자 편의를 위해:

```text

↕

JSON Editor
```

를 동기화한다.

```text

4 → 8
```


반대로 JSON을 수정하면 Form에도 반영한다.

# 98. Plugin Registry

Plugin은 코드 내 단순 switch 문이 아니라 Registry 기반으로 관리한다.

```text
Plugin Registry

├─ SherpaOnnxProvider
├─ ReazonSpeechProvider
├─ FasterWhisperProvider
├─ StyleBertProvider
├─ OpenAIProvider
└─ Future Provider
```

각 Plugin은 다음 정보를 제공한다.

```java
public interface EngineProvider {

    EngineDescriptor descriptor();

    ConfigurationSchema configurationSchema();

    EngineCapabilities capabilities();

    HealthCheckResult healthCheck(
        EngineConnectionProfile profile
    );

}
```

# 101. Source Code Configuration과 Console 연결

개발자가 소스코드에서 설정을 정의하면 Console에서 자동으로 보이도록 하는 구조를 지향한다.

예:

```java
@ConfigurationProperty(
    key = "cpuThreads",
    defaultValue = "4",
    runtimeEditable = true
)
private int cpuThreads;
```

또는 Engine Schema:

```json
{
  "key": "cpuThreads",
  "default": 4,
  "editable": true
}
```

Console은 이를 읽고 자동으로 UI를 생성한다.

따라서:

```text
소스코드 설정

↓

Configuration Schema

↓

Developer Console
```

구조를 유지한다.

# 106. Temporary Runtime Override

개발자 테스트를 위해 일시적으로 설정을 변경하는 기능을 제공할 수 있다.

# 125. 중요한 설계 원칙

관리자 기능 구현 시 다음 원칙을 따른다.

1. 일반 사용자 설정과 관리자 설정을 분리한다.

2. 개발자는 실제 Runtime에 적용된 최종 값을 확인할 수 있어야 한다.

3. 설정값의 원본 Source를 확인할 수 있어야 한다.

4. Source Code Default와 Runtime Override를 구분한다.

5. 모든 Engine 설정은 Schema 기반으로 관리한다.

6. Engine마다 다른 설정 UI를 하드코딩하지 않는다.

7. Form Editor와 JSON Viewer/Editor를 모두 제공할 수 있도록 한다.

8. JSON 변경에는 반드시 Validation을 적용한다.

9. 설정 변경 전 Diff를 확인할 수 있어야 한다.

10. 설정 변경은 Version과 Audit History를 남긴다.

11. 이전 설정으로 Rollback할 수 있어야 한다.

12. Secret은 화면에서 평문으로 노출하지 않는다.

13. API Key 등은 Export 대상에서도 제외한다.

14. Engine마다 Health Check 및 Functional Test를 제공한다.

15. 개발자를 위한 STT/TTS/LLM Playground를 제공한다.

16. End-to-End Speech Conversation Test를 지원한다.

17. 하나의 요청이 어떤 Engine을 거쳤는지 Trace할 수 있어야 한다.

18. Production과 Development 설정을 명확히 구분한다.

19. 위험한 설정은 Restart/Deploy 필요 여부를 표시한다.

20. Production Runtime Override는 기본적으로 제한한다.

# 128. Claude Code 추가 설계 요청

기존 기획서에 본 내용을 병합한 후 다음 설계 작업을 진행한다.

```text
1. Admin Console Information Architecture 설계

2. Role / Permission 모델 설계

3. Engine Configuration Schema 정의

4. Effective Configuration Resolver 설계

5. Configuration Source Priority 정의

6. Configuration Version Entity 설계

7. Configuration Audit Entity 설계

8. Configuration Diff API 설계

9. Configuration Rollback API 설계

10. Raw JSON Configuration API 설계

11. Engine Playground API 설계

12. End-to-End Test API 설계

13. Request Trace 모델 설계

14. Prompt Registry / Versioning 설계

15. Developer Diagnostic API 설계

16. Environment별 Configuration 정책 정의
```

아직 UI 또는 Backend 구현 코드는 작성하지 않는다.

먼저 기존 Domain Architecture와 통합하고:

```text
Domain Model

DB Schema

API Contract

Configuration Resolution Rule

Role / Permission

Module Dependency
```

까지 문서화한 뒤 구현 단계로 진행한다.
