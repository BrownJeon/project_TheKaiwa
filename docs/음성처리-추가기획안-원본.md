# 일본어 회화 앱 추가 기획안

## 25. 추가 설계 목표

기존 Speech / LLM Architecture에 다음 요구사항을 추가한다.

- STT/TTS 엔진을 설정 화면에서 변경 가능
- 일반 사용자와 관리자/개발자 설정 분리
- AI 일본어 선생님 음성을 여러 개 제공
- 외부 작업을 통해 새로운 Voice Model 추가 가능
- 기존 Voice Model 비활성화 및 제거 가능
- Voice의 모든 TTS 설정을 적용한 최종 결과 미리듣기 제공
- STT/TTS Engine별 연결 설정 관리
- Local Engine과 Remote API Engine을 동일한 구조로 관리
- Engine 연결 상태 테스트 기능
- API Key 등 민감 정보는 앱 클라이언트에 저장하지 않음
- LLM, Speech, Learning 영역을 각각 독립적인 Platform Layer로 구성

---

# 26. 사용자용 Speech 설정

일반 사용자에게는 기술적인 엔진 이름보다 사용 목적 중심의 설정을 제공한다.

```text
설정
│
├─ AI 선생님
│    ├─ 목소리
│    ├─ 말하기 속도
│    ├─ 음성 스타일
│    ├─ Pitch
│    ├─ Intonation
│    │
│    └─ ▶ 현재 설정으로 미리듣기
│
├─ 음성 인식
│    ├─ 자동
│    ├─ 빠른 응답
│    ├─ 높은 정확도
│    └─ 오프라인
│
├─ 학습 설정
│    ├─ 일본어 수준
│    ├─ 설명 언어
│    ├─ 교정 빈도
│    └─ 문법 설명 수준
│
└─ 고급 설정
     ├─ Realtime STT Engine
     ├─ Analysis STT Engine
     ├─ TTS Engine
     └─ LLM Engine
```

일반 사용자는 가능한 한 `ReazonSpeech`, `faster-whisper`, `Style-Bert-VITS2` 등의 내부 기술을 알 필요가 없도록 한다.

# 27. AI Teacher Voice를 다중 Voice 구조로 변경

AI 일본어 선생님의 목소리는 하나의 고정된 Voice가 아니라 여러 개의 Voice Profile 중 사용자가 선택할 수 있도록 한다.

예:

```text
AI 선생님 목소리

○ Haruka
  밝고 친절한 목소리

○ Sakura
  차분하고 부드러운 목소리

○ Yui
  자연스럽고 편안한 회화 스타일

○ Takumi
  낮고 안정적인 목소리

○ Kenta
  밝고 활기찬 남성 목소리
```

Voice 수는 애플리케이션 코드에 고정하지 않는다.

Voice Registry에서 동적으로 조회한다.

# 28. Style-Bert-VITS2와 Multi Voice

Style-Bert-VITS2는 여러 모델을 `model_assets` 아래에서 관리할 수 있으며 각 모델은 대략 다음 구조를 가진다.

```text
model_assets/

├─ teacher_haruka/
│    ├─ config.json
│    ├─ haruka.safetensors
│    └─ style_vectors.npy
│
├─ teacher_sakura/
│    ├─ config.json
│    ├─ sakura.safetensors
│    └─ style_vectors.npy
│
└─ teacher_takumi/
     ├─ config.json
     ├─ takumi.safetensors
     └─ style_vectors.npy
```

Style-Bert-VITS2 공식 문서 역시 `model_assets` 아래 여러 모델을 두는 구조와 `style_vectors.npy`를 통한 스타일 제어를 지원한다.

따라서 AI Teacher Voice를 새로운 데이터처럼 추가하는 구조로 설계할 수 있다.

# 29. Voice와 Speaker 분리

Voice Profile에서는 다음 개념을 구분한다.

```text
Model
  ↓
Speaker
  ↓
Style
```

하나의 모델에 여러 Speaker가 존재할 수도 있다.

Style-Bert-VITS2 API 역시 `model_name/model_id`, `speaker_name/speaker_id`, `style`, `style_weight` 등을 별도의 파라미터로 처리한다.

따라서 애플리케이션 내부에서는 이를 `VoiceProfile`이라는 하나의 논리적 객체로 추상화한다.

# 31. Voice Registry

Voice를 코드 내부 Enum으로 관리하지 않는다.

별도 Voice Registry를 구성한다.

```text
Voice Registry

├─ teacher_haruka
├─ teacher_sakura
├─ teacher_yui
├─ teacher_takumi
└─ ...
```

Voice Registry는 다음 책임을 가진다.

```text
Voice 조회
Voice 등록
Voice 수정
Voice 비활성화
Voice 삭제
Voice Model 연결
Speaker 연결
Style 조회
Preview 생성
Voice 상태 관리
```

# 32. 외부 Voice 추가 기능

운영자는 새로운 Style-Bert-VITS2 Voice Model을 외부에서 학습한 뒤 애플리케이션에 추가할 수 있어야 한다.

예:

```text
Voice Training Environment

       ↓

teacher_mio.zip

       ↓

Voice Import Service

       ↓

Validation

       ↓

model_assets/teacher_mio

       ↓

Style-Bert Model Refresh

       ↓

Voice Registry 등록

       ↓

앱에 Mio Voice 표시
```

Voice 학습 시스템과 실제 서비스 시스템은 반드시 같은 시스템일 필요가 없다.

즉:

```text
Training Server
      ↓
Voice Package
      ↓
Production TTS Server
```

구조를 허용한다.

# 34. Voice Import 과정

새 Voice를 추가할 때 다음 검증 단계를 거친다.

```text
Upload Voice Package

        ↓

        ↓

Manifest Validation

        ↓

Model File Validation

        ↓

TTS Test

        ↓

Registry Registration

        ↓

Activate Voice
```

등록에 실패한 Voice는 사용자에게 노출하지 않는다.

---

# 35. Style-Bert Model Refresh 연동

Style-Bert-VITS2에는 현재 로딩된 모델 정보를 조회하는 `/models/info`와 모델 경로가 추가 또는 삭제된 경우 재검색하는 `/models/refresh` API가 존재한다. `/models/info`는 model path, speaker mapping, style mapping 등의 정보도 반환한다.

따라서 Voice Import 이후:

```text
Voice Package Import

↓

model_assets 변경

↓

POST /models/refresh

↓

GET /models/info

↓

Voice Registry 동기화
```

형태의 Adapter를 구성할 수 있다.

Style-Bert 자체 API를 모바일 앱이 직접 호출하지 않고 반드시 `TTS Service`가 감싼다.

---

# 36. Voice 제거 정책

Voice 삭제는 즉시 파일 삭제보다는 두 단계로 나누는 것을 권장한다.

```text
ACTIVE

↓

DISABLED

↓

ARCHIVED / DELETED
```

`DISABLED` 상태에서는 신규 사용자가 선택할 수 없지만 기존 대화 기록이나 설정 정보는 유지한다.

Voice를 참조하는 사용자가 존재하는 경우:

```text
teacher_mio
   ↓
DISABLED
```

처리 후 사용자 기본 Voice를 다른 Voice로 변경한다.

물리적인 Model 삭제는 별도 관리 작업으로 수행한다.

# 39. AI Voice 설정

Voice 선택 외에도 사용자는 다음 설정을 변경할 수 있다.

```text
Voice

Style

Speed

Pitch

Intonation
```


# 40. 통합 미리듣기

각 설정마다 별도의 Preview 버튼을 만들지 않는다.

사용자가 현재 선택한 **모든 Voice 설정을 적용한 최종 결과를 한 번에 미리듣는 방식**으로 구현한다.

예:

```text
AI 선생님

목소리
Haruka

스타일
Friendly

속도
0.9x

Pitch
1.0

Intonation
1.1


        ▶ 현재 설정으로 미리듣기
```

사용자가 미리듣기를 누르면 현재 화면의 모든 임시 설정값을 TTS에 전달한다.

설정을 저장하기 전에도 Preview가 가능해야 한다.

# 43. Preview 문장

기본 Preview 문장은 모든 Voice에 동일한 일본어 문장을 사용한다.

예:

```text
こんにちは。
今日も一緒に楽しく日本語を勉強しましょう。
```

동일한 문장을 사용하면 사용자가 Voice 차이를 비교하기 쉽다.

향후 운영 설정에서 Preview 문장을 변경할 수 있도록 한다.

```text
voice.preview.defaultText
```

Preview 요청마다 LLM을 호출하지 않는다.

# 46. Advanced Speech Engine 설정 보완

Advanced Speech Engine 설정에서는 단순히 Engine 이름만 선택해서는 안 된다.

다음 두 개를 분리한다.

```text
Engine

+

Engine Connection Profile
```

예:

```text
Realtime STT Engine

ReazonSpeech

Connection

Local Reazon #1
```

또는:

```text
TTS Engine

Style-Bert-VITS2

Connection

Mac Mini TTS Server
```

상용 API라면:

```text
TTS Engine

External TTS Provider

Connection

Production TTS Account
```

형태가 된다.

# 47. Engine과 Connection Profile 분리 이유

하나의 Engine을 여러 환경에서 사용할 수 있기 때문이다.

예:

```text
Style-Bert-VITS2

├─ Local Mac Mini
├─ Development GPU Server
└─ Production GPU Server
```

또는:

```text
OpenAI

├─ Development Project
└─ Production Project
```

따라서:

```text
Engine
=
어떤 기술을 사용할 것인가

Connection Profile
=
그 기술을 어디에서 어떤 설정으로 사용할 것인가
```

로 구분한다.

# 52. Local Engine Connection 설정

Local Engine도 별도의 연결/실행 설정이 필요하다.

예를 들어 faster-whisper는 모델 이름 또는 모델 경로, CPU/GPU device, compute type, thread 등의 설정을 제공한다.

예:

```json
{
  "id": "whisper-local",

  "engineId": "faster-whisper",

  "runtime": {
    "model": "large-v3",

    "device": "auto",

    "computeType": "default",

    "cpuThreads": 4,

    "workers": 1
  }
}
```

---

# 53. sherpa-onnx Connection 설정

sherpa-onnx는 모델 종류에 따라 encoder, decoder, joiner 또는 단일 ONNX 모델 경로가 필요하며 provider, thread, decoding method 등의 runtime 설정도 존재한다.

예:

```json
{
  "id": "sherpa-reazon-local",

  "engineId": "sherpa-onnx",

  "runtime": {
    "provider": "cpu",

    "numThreads": 4,

    "decodingMethod": "greedy_search",

    "model": {
      "encoder": "...",
      "decoder": "...",
      "joiner": "...",
      "tokens": "..."
    }
  }
}
```

이 설정은 일반 사용자가 변경하지 않고 관리자 또는 개발자 설정에서 관리한다.

# 75. 핵심 구현 원칙

1. Voice는 애플리케이션 코드가 아니라 데이터로 관리한다.

2. AI Teacher Voice는 복수 개 등록 가능해야 한다.

3. 새로운 Voice를 외부 Training Environment에서 만들어 Import할 수 있어야 한다.

4. Voice 삭제는 Disable → Archive/Delete의 단계로 처리한다.

5. Style-Bert 모델 변경 후 Registry를 재동기화할 수 있어야 한다.

6. Voice/Speaker/Style은 서로 다른 개념이지만 사용자에게는 Voice Profile로 단순화한다.

7. 미리듣기는 각 옵션별 버튼이 아니라 현재 모든 설정을 합친 하나의 결과를 들려준다.

8. Preview는 설정 저장 전 Draft 상태에서도 가능해야 한다.

9. Engine 선택과 Engine Connection 설정은 반드시 분리한다.

10. 하나의 Engine에 여러 Connection Profile을 등록할 수 있어야 한다.

11. Local Engine도 Model/Device/Runtime 설정을 Connection Profile로 관리한다.

12. Remote Engine의 Credential은 모바일 앱에 저장하지 않는다.

13. Engine마다 다른 설정 항목은 Configuration Schema 기반으로 처리한다.

14. 모든 Connection에는 Health Check와 Functional Test를 제공한다.

15. 장애 발생 시 Engine Fallback을 지원할 수 있도록 한다.

16. LLM/TTS/STT는 모두 Adapter 기반 Plugin Architecture를 유지한다.
